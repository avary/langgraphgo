Implementation Notes

Issue #101 — Converge the plan-execute prebuilt agents — 2026-07-08

Design Decisions

Decision Unify the option surface instead of merging the agents

Ambiguity: The issue asked to "converge" CreatePlanningAgent, CreateManusAgent and CreatePEVAgent, implying they were redundant variants of one pattern.

Choice: Kept all three factories and their distinct graph topologies; converged only the configuration API by making all three accept the shared CreateAgentOption functional options.

Rationale: The three agents are genuinely different execution graphs (single-shot DAG vs. filesystem-persistent phase loop vs. plan-execute-verify retry loop). Merging them into one factory would produce a leaky mega-constructor. Converging the option surface removes the real inconsistency (three different config idioms) without destroying working, distinct behaviors.

Decision Config-struct fields take precedence over options

Ambiguity: When both a legacy config struct and a functional option set the same field, which wins?

Choice: Non-zero config-struct fields win; options only fill fields the caller left unset (implemented in applyManusOptions / applyPEVOptions).

Rationale: Preserves the exact behavior of every existing caller that passes a fully-populated config. Options become purely additive, so no current code path changes.

Deviations

Deviation Did not remove or merge any agent factory

Spec said: "Converge" the planning agents, which reads as consolidate/remove duplication.

Implemented instead: A non-breaking convergence — deprecated ManusConfig and PEVAgentConfig via godoc, kept them working, and unified only the option-passing API.

Why better: The issue's premise (that the three are convergeable variants) is contradicted by the code: they have distinct topologies and live example programs and tests reference each. A hard merge would break examples/manus_agent, examples/pev_agent, and the prebuilt test suite for no design gain.

Tradeoffs

Tradeoff Shared option struct vs. per-agent option types

Alternatives: (a) one shared CreateAgentOptions with agent-specific fields; (b) a separate option type per factory.

Pros/cons: (a) gives callers one consistent import and With* vocabulary but carries fields not every factory reads; (b) is tightly scoped per agent but reintroduces the very API divergence the issue complains about.

Why chosen: (a) — the whole point was a single consistent surface. Field applicability is documented in the struct godoc so the extra fields are discoverable, not confusing.

Tradeoff Two near-identical apply* helpers vs. one generic folder

Alternatives: keep applyManusOptions and applyPEVOptions separate, or extract a reflection/generic merge.

Pros/cons: separate helpers duplicate ~6 lines each but stay type-safe and trivially readable; a generic merge would need reflection and obscure the precedence rule.

Why chosen: two small explicit helpers — they operate on different config types and the duplication is cheaper than the abstraction.
